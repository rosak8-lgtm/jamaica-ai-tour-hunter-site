# JAMAICA — восстановленный рабочий контекст сайта, 23.11.2026

> Точка продолжения **веб-сайта туристического агентства** JAMAICA. Источники: переписка «Восстановление проекта Jamaica», «Продолжение разработки Jamaica», «Продолжение разработки сайта Jamaica»; существующие документы `docs/JAMAICA_PROJECT_MASTER_HANDOFF_20261122.md`, `docs/JAMAICA_TRAVELER_GROUPS_BG_INTEGRATION_20261122.md` и исходный код. Это не автоматическое свидетельство живой доступности API или продажи.

## Бизнес-цель и принятый UX-контракт

Клиент должен **на сайте JAMAICA** пройти путь **поиск → полный список реальных опубликованных вариантов → карточка тура и гостиницы → точная котировка на состав → проверка отеля/двух рейсов → договор → платёж → подтверждённая бронь**. Отсутствие разрешённой интеграции не заменять WhatsApp, Telegram, «напишите менеджеру» или фиктивной кнопкой оплаты. Интерфейс по удобству близок к travel search / Tourvisor, без копирования чужого кода, бренда или дизайна.

Фирменные цвета: фиолетовый, бирюзовый, золотой. Фирменный попугай **в очках** — в шапке/баннере/favicon. Мобильный поиск и даты удобны; в выдаче важнее реальные карточки, чем служебные статистические стены. На фото не размещать навязчивые надписи «Фото направления · не фото гостиницы»; подпись авторства/лицензии допустима вне изображения. Нельзя выдавать фотографию страны за фотографию конкретного отеля.

Поиск и фильтры: вылет прежде всего из Иркутска, все направления **с реально опубликованными прайс-листами**, другие города только по доступным источникам; страна/курорт/отель, даты/месяцы (включая 2027), длительность, питание, бюджет, сортировка, избранное, раскрытие всех результатов с догрузкой. Нельзя обещать весь рынок, если это ограниченный снимок. Бюджет 2 взрослых нельзя автоматически применять к другой группе.

Состав: 1–5 отдельных номеров, до 12 взрослых и 10 детей в интерфейсе; фактический возраст каждого ребёнка на дату вылета. Сохранить состав между поиском, подробностями и формой запроса. Никогда не подставлять выдуманный возраст ребёнка, не умножать «цену за двух взрослых» на количество гостей или комнат.

Активные источники в данном проекте — **Библио-Глобус и PEGAS Touristik**. PEGAS не приписывать предложения BG, самостоятельная интеграция сайта ещё не подтверждена. Для BG при отборе **подтверждённых горящих туров** требуется сначала точная метка **«ЛУЧШАЯ ЦЕНА» на выбранном маршруте**, затем оба зелёных статуса рейсов в той же строке/сеансе, потом цена/комнаты/места. Для PEGAS правило метки BG не действует. Обычный публичный список предварительных прайс-листов не надо искусственно прятать из-за отсутствия финального подтверждения; отдельный необязательный фильтр проверенных визуальных наблюдений допустим, если доказательства свежие.

## Техническая топология

- Репозиторий: https://github.com/rosak8-lgtm/jamaica-ai-tour-hunter-site
- Публичный сайт: https://rosak8-lgtm.github.io/jamaica-ai-tour-hunter-site/
- GitHub Pages — клиентская публикация. Она **не подтверждает** обновление приватного Python/Oracle.
- `index.html` — поисковая выдача; `hotel.html`, `preview.html`, `quote.html`, `checkout.html` — этапы карточки и заказа. `scripts/traveler-party.js` и `scripts/traveler-ui.js` — состав/группы.
- `tour-previews.json` — первые до 8 000 только **предварительных** записей; `tour-previews-shards/part-*.json` — остальные до суммарных 60 000. `scripts/catalog-shards.js` проверяет схему/ограничения; GitHub Pages загружает шардированные файлы, а `index.html` показывает страны по мере поступления новых проверенных разделов.
- `scripts/oracle_site_publisher.py` — 5-минутная серверная публикация каталога. Наличие активного systemd timer **не доказывает** успешность каждого import. Из предыдущего инцидента `GENERATED_FEED_INVALID_SIZE` важен отдельный PASS в журнале Oracle, см. `docs/JAMAICA_ORACLE_GENERATED_FEED_SIZE_REPAIR_20261123.md`.
- `verified-offers.json` и `tour-visual-evidence.json` — отдельные, строгие, защищённые от неверных статусов фиды. На последней ручной проверке GitHub 23.11 оба без подтверждённых записей. `checkout-config.json`: `live_booking_enabled=false`, `payments_enabled=false`, `contract_first_enabled=false`.
- `hotel-enrichment.json` — факты/галереи ограниченного числа отелей; `hotel-media-approved.json` и `hotel-official-sites.json` на проверке 23.11 не содержали одобренных hotel-ID. `assets/jamaica-destination-media.json` содержал изображения направлений для 13 стран. Для реальной карточки нужен точный hotel ID + лицензированное фото/HTTPS URL. Внешние фото допустимы только при проверенных правах и доступности.

## Оставшиеся реальные блокеры перед онлайн-продажами

1. **Приватный авторизованный quote adapter**, которого пока нет в полноценной цепочке сайта. Должен для выбранного `preview_id`/состава надёжно связать актуальный `prx`, `countryId`, `templateId` **или** `comissionId`, `dt`, `roommeal`, `sr`, возрастный `ag` и (при наличии) точный `otv` от одного официального прайс-листа; проверить реальные даты рождения, совместимость групп и фактическую цену **всего состава** через допущенный API. Не передавать паспорта, DOB, пароли, токены в query string/GitHub.
2. Независимо проверить доступность всех номеров, stop-sale и обоих рейсов в выбранном маршруте/тарифе; для BG — точную метку «ЛУЧШАЯ ЦЕНА» без переноса с другого маршрута/даты. Источник `novirt=0` требуется для выбора конкретного рейса через `sr` по официальному протоколу.
3. Продуктовый `POST /v1/preview-quotes` с приватной сессией, TTL/idempotency, отдельной ценой для каждого состава и явным отображением состояния `QUOTE_PENDING`/`NOT_AVAILABLE`. Никакого `bookable=true` до всех trust gates.
4. Лицензированные фото конкретных отелей с проверкой hotel ID, доступности и прав; заполнить реальные media manifests без фальшивого hotel match.
5. Подтверждённые юридические полномочия продавца, договор, обработка ПДн, электронная подпись, PSP, повторные проверки цены после подписания/оплаты и idempotent supplier booking. Только тогда включать `checkout-config.json` опциями.
6. PEGAS — отдельная авторизованная интеграция, без приписывания метки BG. Не добавлять сторонние операторы до нового согласованного решения.

## Командная практика продолжения

Каждый следующий этап: изучить фактический `main` и CI → отдельная ветка/PR → синтетические и контрактные тесты → успешный CI/Chromium → merge → **отдельный** read-only аудит Oracle → безопасный stage с резервной копией и логами → только затем production. ## Продолжение — отображение дополнительных стран и месяцев (23.11.2026)

Задача: реальные предложения других стран должны появляться в выдаче **сразу после загрузки первого файла**, а не только когда скачаны до 13 больших разделов. Никаких несуществующих туров, чужих цен, разрешения бронирования или изменения границ 60 000 записей.

- `scripts/oracle_site_publisher.py`: `diverse_root_and_remaining` выбирает до 8 000 первых **существующих** записей циклически по стране и фактическому месяцу вылета. Сначала Таиланд, Китай, Вьетнам, затем остальные опубликованные страны. Внутри месяца приоритет свежим price-list записям с известной справочной ценой, не подменяя неизвестные цены. Остаток до 60 000 выходит в те же безопасные JSON-шарды. Каждая запись сохраняется **ровно один раз**; все поля поставщика неизменны. Наличие страны/месяца означает лишь публикацию предварительного прайс-листа, не проверку мест.
- `scripts/country-offer-balance.js`: при поиске **без выбранной страны** первые результаты чередуют реальные направления, сохраняя приоритет Таиланд → Китай → Вьетнам. Избранная пользователем сортировка «самые дешёвые по всем странам» остаётся отдельной и сознательно глобальной. Выбор страны из быстрых кнопок и бокового фильтра доступен по реально опубликованным вариантам **из выбранного города вылета**, не из чужого аэропорта.
- `scripts/catalog-shards.js`: одна недоступная или недействительная часть не скрывает остальные успешно валидированные страны из той же группы. Для каждой части предусмотрена одна повторная попытка. Если части действительно отсутствуют, интерфейс **обязан сообщить, что каталог неполный**. Детальная ссылка на тур из доступного раздела остаётся рабочей, но по неполной загрузке нельзя объявлять отсутствующий тур несуществующим.
- Тесты: `backend.test_oracle_site_publisher`, `scripts/test-catalog-shards.mjs`, `scripts/test-country-offer-balance.mjs`, `scripts/test-site.mjs` и полный Chromium smoke.

**Граница внедрения:** новая балансировка root **начнёт влиять на реальный опубликованный каталог только после того, как работающий Oracle publisher применит обновлённый Python из `main` и успешно выпустит очередной feed.** GitHub Pages CI/PASS сам по себе это не доказывает. Улучшения браузерного порядка и обработки отсутствующих шардов действуют после успешной публикации frontend main. Проверить Oracle owner-only journal и число стран, опубликованных в первых 8 000 строк; не включать неподтверждённые продажи.

### Клиентские быстрые месяцы вылета

`scripts/month-offer-filters.js` и `index.html#quickMonths`: навигация «Все даты», «Декабрь 2026», «Январь 2027» и **любые другие месяцы, реально имеющиеся в опубликованных данных**. Месяц отображается только при наличии записей из выбранного города вылета и выбранной страны; у несуществующего месяца нет фиктивного счётчика. По клику заполняются точные границы календарного месяца в полях дат и вызывается настоящий поиск. Пользовательский диапазон произвольных дат не маскируется под «Все даты». На мобильном месяцы доступны через горизонтальную прокрутку, без чрезмерного списка на экране. Реальная цена/два рейса/статус бронирования по-прежнему требуют авторизованной проверки, включать оплаты нельзя.

Тест: `node scripts/test-month-offer-filters.mjs` (включён в CI). Проверяет декабрь 2026 и 2027, високосный февраль 2028, неверные даты и привязку к стране/городу.
