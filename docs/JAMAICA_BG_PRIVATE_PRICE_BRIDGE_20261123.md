# JAMAICA — приватный расчёт цены всего состава, V1 (23.11.2026)

## Что реализовано

Три уже существующих уровня сохранены, теперь дополнены четвёртым:

1. Аутентифицированные **частные** прайс-листы Библио-Глобуса → \`private_source_candidates\` в \`backend/bg_private_source_crosswalk.py\`. Все источники одной цены и номера должны быть получены из того же самого \`prx\`, \`templateId\` либо \`comissionId\`, \`roommeal\`, \`sr\`, \`ag\`, \`otv\`.
2. \`select_exact_party_sources\` в \`backend/bg_private_exact_party.py\` → только варианты с **фактическими возрастами на дату вылета**, общим источником, датой проживания и одним маршрутом.
3. **НОВОЕ** \`price_exact_party_read_only\` в \`backend/bg_private_quote_bridge.py\` → получает валидную авторизацию покупателя, отдельное частное подтверждение конкретных номеров, тарифа, суммарной вместимости и \`sr\` из выгрузки с \`novirt=0\`. Внутри выбранного source-plan передаёт неизменные supplier IDs в \`BGReadOnlyPriceClient.price_groups_only\` — ровно **один** price-only запрос, без \`<confirm/>\`.
4. Существующий Tour API XML parser → сумма \`fullamount\` всего тура в **RUB**, а не агентская \`amount\` и не валютная альтернатива. Ответ \`PRICE_ONLY_NOT_BOOKABLE\` не содержит паспорта, ФИО, DOB, supplier IDs или непроверенных цен каждого номера.

Официальные инструкции:
- https://www.bgoperator.ru/texts/api/tour-api.html
- https://www.bgoperator.ru/texts/api/load-xml-prices-en.html

## Принцип безопасности — чего НЕТ в текущем GitHub Pages

**НЕ введены** публичный \`POST /v1/preview-quotes\`, сбор паспортных данных через статический сайт, Orion/Oracle-сервис авторизации покупателя, подтверждение оператора о суммарной вместимости, подписанное доказательство \`novirt=0\`, хранение пользовательской сессии, пользовательский договор, PSP или бронирование.

Точно так же \`IndependentOperatorPreflight\` — интерфейс для **будущего серверного источника фактов**, а не их генератор. Разработчик не должен выставлять четыре его флага по \`prices[].ag\`, \`stop=false\`, двум зелёным значкам или просто наличию \`ExactPartySourcePlan\`. Флаги требуют реальной независимой проверки у уполномоченного поставщика, связанной с тем же buyer session, точно выбранными \`otv\`, \`roommeal\`, \`sr\`, датой и количеством **всех** номеров. Если нет согласованного доказательства — **не вызывать API**. Старое визуальное правило для лучших горящих предложений BG (сначала «ЛУЧШАЯ ЦЕНА» на конкретном маршруте, затем два зелёных статуса) остаётся отдельной проверкой и **не заменяется** read-only ценой.

\`PrivateBuyerPriceAuthorization\` также обязан создаваться **только** защищённым приватным middleware после реальной аутентификации и проверки согласия на работу с персональными данными и разрешённого supplier API. Создавать такой объект на основании browser JSON, query string или preview нельзя. Секреты BG не пишутся в репозиторий и не уходят в JS-клиент.

У источника цен может быть первичная дата вылета и более поздняя дата начала отеля в пределах 0–4 дней; выбранные номера обязаны иметь одну дату размещения и маршрут. Младенцы требуют подтверждённых тарифов и правила места/без места, не угадываемого из возраста.

Integration test \`backend/test_bg_private_quote_bridge.py\` использует исключительно синтетические имена/паспорта и fake opener: проверяет **настоящую сериализацию** двух номеров и POST с \`<otv>\` от отдельных точных возрастных вариантов, RUB \`fullamount\`, запрет \`<confirm/>\`, согласие, срок действия source evidence, общий маршрут, защиту от чужого supplier source, младенцев и отсутствие утечки данных. Никаких реальных login/passport, сетевых запросов к BG или платежей тест не делает.

## Что требуется для продающего сайта следующим шагом

В Oracle **приватно**, вне Pages, реализовать отдельный проверяемый сервис, который:
1. Проверяет покупательскую сессию и корректный состав номеров; принимает DOB и документы **только** после предоставления HTTPS, законных оснований обработки и протокола конфиденциальности.
2. По выбранному \`preview_id\` загружает свежую аутентифицированную приватную выгрузку (\`novirt=0\`), создаёт candidates и производит реальную independent option/batch-room проверку.
3. Только с подтверждённым supplier API доступом и доказательствами вызывает \`price_exact_party_read_only\`, записывает ответ в **приватную** сессию c TTL и не публикует PII в GitHub.
4. Отдельно проверяет оба рейса, stop sale, выбранный отель, законную продажу агентством, договор, оплату, переход к подтверждению заказа. Не использовать цену-only как автоматическое разрешение на бронь.

Текущий статус: технический код для приватной цены готов к работе после внедрения доверенного источника preflight, но **LIVE-запросы и реальные продажи не подтверждены**.

## Подготовленная клиентская цена для 1–5 номеров (без действующего API)

В \`quote.html\` предусмотрен **отдельный** read-only этап \`POST /v1/party-price-checks\`.
Он НЕ зависит от включения договора или эквайринга. В \`checkout-config.json\`
два независимых тумблера \`price_checks_enabled=false\` и
\`private_price_api_enabled=false\` оставлены выключенными.

Включить их допустимо только после реального развертывания авторизованного
приватного сервиса на HTTPS с \`auth_api_enabled=true\`. Отсутствующий сервис не
имитируется. Публичная страница может отправить только:

\`\`\`json
{"preview_id":"p_<24-hex>","rooms":[{"adults":2,"child_ages":[6,12]},{"adults":1,"child_ages":[4]}]}
\`\`\`

Это возраст на вылет и состав номеров; **НЕ** даты рождения, паспорт, цена,
платёжные данные или raw supplier-source IDs. Сервис обязан брать истинные
DOB, идентичности, согласие и private-source price-list из **своего**
защищённого покупательского контекста и самостоятельно вызывать preflight и
\`price_exact_party_read_only\`. Если в сессии ещё нет необходимых разрешённых
данных, отвечать **не 200 с выдуманной ценой**, а отказом / отдельным
законным приватным процессом их предоставления.

Только если цена реально получена, сервер может ответить:

\`\`\`json
{
  "status":"PRICE_ONLY_NOT_BOOKABLE",
  "source_preview_id":"p_<24-hex>",
  "total_rub":185000,
  "currency":"RUB",
  "groups_requested":2,
  "supplier_total_scope":"WHOLE_TOUR",
  "supplier_price_readonly":true,
  "expires_at":"2026-11-23T12:04:30+00:00",
  "quote_verified":false,
  "availability_verified":false,
  "flight_verified":false,
  "best_price_verified":false,
  "bookable":false,
  "booked":false,
  "payment_enabled":false
}
\`\`\`

Это **пример протокола**, а не цена реально доступного тура. Страница
проверяет количество выбранных комнат, source preview ID, весь состав,
валидность суммы, срок не более 10 минут, отсутствие права на покупку и
строгие \`false\` для всех статусов доступности. Цена выводится как
**стоимость за весь состав**, без кнопки договора/оплаты.

Существующий путь подтверждённой цены для двух взрослых
\`POST /v1/preview-quotes\` не заменяется или не подменяется.
Когда весь стек бронирования выключен, но приватная price-only проверка
в будущем разрешена, два взрослых тоже могут использовать новый путь.
Переход к покупке требует отдельной независимой проверки отеля, обоих
рейсов, правил BG и подписания договора.

Проверка клиентского кода:

\`\`\`bash
node scripts/test-quote-price-only.mjs
\`\`\`

Тест имитирует сервер, проверяет передачу всех комнат и детских возрастов,
отсутствие PII, отклонение ошибочного \`bookable=true\`, истёкшей цены и
статуса \`QUOTE_READY\` в read-only контуре. Тест не отправляет запросов
во внешние сервисы и не изменяет настоящие цены.
