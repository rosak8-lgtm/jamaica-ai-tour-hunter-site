# JAMAICA — единое техническое задание и точка продолжения (21.11.2026)

> Рабочий документ восстановления контекста сайта. Факты разделены на проверенные в GitHub, исторические журналы и неподтверждённую production-доступность. Это не инструкция имитировать бронирование.

## 1. Цель и границы продукта
**JAMAICA Website** — собственный туристический поисковик: поиск → варианты → конкретный отель → конкретный тур → перепроверка живой цены и наличия → договор → оплата → бронирование/документы в интерфейсе JAMAICA. До завершения официальных интеграций поздние шаги должны оставаться заблокированными и честно объясняться посетителю.

Отдельно существует **JAMAICA Telegram Tour Hunter**. Работа над сайтом не должна включать отправку Telegram, изменять строгие правила публикации «горящих» туров, перезапускать сканеры или расширять список операторов.

## 2. Неизменяемые требования из связанных чатов
- Сохранять существующий GitHub-проект `rosak8-lgtm/jamaica-ai-tour-hunter-site`. Не переписывать его заново.
- UX в логике Tourvisor: форма поиска, боковые фильтры, понятные горизонтальные карточки туров, избранное, мобильный интерфейс, детальная страница гостиницы и тура. Не копировать бренд или чужие изображения Tourvisor.
- Фирменный стиль JAMAICA: пурпурный, бирюзовый, жёлтый. Сохранить утверждённого фирменного попугая; не заменять его сторонним персонажем.
- Поиск без обязательной конкретизации: город вылета по умолчанию Иркутск, необязательная страна, дата/диапазон, 3–180 ночей, состав туристов, курорт, отель, бюджет. Показывать все фактически опубликованные подходящие варианты, а не только три выбранные страны или только 3/4/7 ночей.
- Приоритет мониторинга: Таиланд → Китай → Вьетнам; остальные доступные страны не исключать. Активные операторы в backend: Библио-Глобус и PEGAS; третьих без отдельного решения не включать. В пользовательском поисковом интерфейсе не продвигать названия операторов.
- Карточка выбора ведёт на страницу сведений об отеле/туре, **не** прямо на оплату, WhatsApp, обращение к менеджеру или внешний сайт.
- Только идентифицированные фотографии выбранного отеля с разрешённым коммерческим использованием и атрибуцией. Прямой HTTPS URL без загрузки на Oracle допустим при наличии прав и технической доступности. Фото города не выдавать за фото отеля. Booking/Tripadvisor без лицензии не подключать.
- Не выдавать предварительную прайс-цену за подтверждённую бронь. Для семьи не умножать цену на место и не подменять котировку для двоих.
- Хорошая адаптация под мобильные, доступность с клавиатуры, адекватные подписи полей, ошибки/пустые результаты, быстрый ответ браузера и честные статусы.
- Не трогать боевой Oracle, DNS, PostgreSQL, сервисы Telegram/бота или торговые данные без соответствующей подтверждённой проверки и безопасного плана изменения.

Ранее была подготовлена архитектура каталога с несколькими JSON-частями и потолком до 60 000 предварительных вариантов; это **верхняя возможность публикации**, не доказанное число реально импортированных туров.

Тестовая интеграция HBX/Hotelbeds вернула метаданные 10 гостиниц и 1084 фотопутей в одном диагностическом запросе. TEST/PRUEBAS — не лицензия на коммерческий показ. Открытые фото Wikimedia Commons есть для отдельных реально сопоставленных гостиниц с учётом лицензий и атрибуции. Нет доказательства заполнения галерей большинства гостиниц.

## 5. Политика поиска, актуальности и бронирования
- Различать `PREVIEW` (прайс-лист), `QUOTE_VERIFIED` (официальная актуальная котировка), `BOOKING_CONFIRMED` (поставщик подтвердил заказ) и `PAID` (платёж действительно подтверждён). Не перескакивать стадии.
- На сайте без подтверждённого API **не** обещать доступное место, прямую оплату или подтверждённое бронирование; показывать дату и источник справочной цены.
- При бюджетном поиске для двух взрослых предложения без известной цены не должны классифицироваться как подходящие. При ином составе честно обозначать необходимость отдельного расчёта.
- Выбранная страна из справочника не должна исчезать из формы только потому, что опубликованная выборка для неё пуста.
- Не использовать непроверенные URL изображения/неавторизованные CDN и не подставлять фото другой гостиницы.
- Строгие критерии «два зелёных самолётика» и BG «ЛУЧШАЯ ЦЕНА» остаются особыми правилами Telegram-публикации. Нельзя незаметно смешивать строгий горячий фильтр с нейтральным веб-каталогом предварительных туров.
- Проверять реальные ограничения поставщика на частоту запросов. Исторический запуск каталога на Oracle каждые 5 минут не означает разрешения опрашивать каждый операторский endpoint каждые 5 минут.

## 6. Приоритеты следующей разработки
### P0 — точность и надёжность веб-поиска
1. Пройти CI, Chromium desktop + mobile и ручные сценарии: все страны, свободный поиск, длительности 3–180, дальние месяцы, бюджет, состав гостей, пустая выдача, избранное.
2. Сверить production-выгрузку с source scope: точное число стран/вариантов, возраст данных, частичные ошибки JSON-шардов, отсутствие «нулевой выдачи» при сбое части.
3. Не допускать ложных отрицательных результатов при частичной загрузке / смене страны / мобильных фильтрах.
4. Сверить настоящую публикацию GitHub Pages и фактические HTTP-ответы — GitHub-коммит сам по себе не production E2E.

### P1 — реальные фотографии и содержательные карточки
1. Массовый каталог фото **только** по договорно лицензированному ID crosswalk или подтверждённым Commons-снимкам, с проверками происхождения, лицензии и согласованного названия/страны/ID.
2. Проверка загрузки CDN, image fallback, lazy loading, авторства и кликабельного фотоисточника.
3. Чёткое разделение фактов об отеле, номере, типе питания и об условиях конкретного пакета.

### P2 — собственный процесс продаж
1. Подтвердить юридическую модель продажи, договор с поставщиком, API живой котировки и условия перепроверки авиамест и гостиницы.
2. Реализовать защищённый backend оформления, идемпотентные заявки/заказы, подтверждение условий, договор, платёж и сверку состояния заказа.
3. Только после end-to-end тестов и разрешений включать sale flags, оплату и реальное бронирование. Запрещена демонстрационная «оплачено» без платежа.

## 8. Критерий «готовый рабочий сайт»
«Работает поиск» = поисковая форма возвращает реальные source-backed предварительные записи; «можно купить» = подтверждены API котировки, стоимость, наличие, юридические условия, договор, платёж, бронь и документы. Ни одно из этих утверждений не выводить только из числа тестов или успешной публикации статического фронтенда.
