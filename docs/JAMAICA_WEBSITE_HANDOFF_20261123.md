# JAMAICA — восстановленный рабочий контекст сайта, 23.11.2026

> Точка продолжения **веб-сайта туристического агентства** JAMAICA. Источники: переписка «Восстановление проекта Jamaica», «Продолжение разработки Jamaica», «Продолжение разработки сайта Jamaica»; существующие документы `docs/JAMAICA_PROJECT_MASTER_HANDOFF_20261122.md`, `docs/JAMAICA_TRAVELER_GROUPS_BG_INTEGRATION_20261122.md` и исходный код. Это не автоматическое свидетельство живой доступности API или продажи.

## Бизнес-цель и принятый UX-контракт

Клиент должен **на сайте JAMAICA** пройти путь **поиск → полный список реальных опубликованных вариантов → карточка тура и гостиницы → точная котировка на состав → проверка отеля/двух рейсов → договор → платёж → подтверждённая бронь**. Отсутствие разрешённой интеграции не заменять WhatsApp, Telegram, «напишите менеджеру» или фиктивной кнопкой оплаты. Интерфейс по удобству близок к travel search / Tourvisor, без копирования чужого кода, бренда или дизайна.

Фирменные цвета: фиолетовый, бирюзовый, золотой. Фирменный попугай **в очках** — в шапке/баннере/favicon. Мобильный поиск и даты удобны; в выдаче важнее реальные карточки, чем служебные статистические стены. На фото не размещать навязчивые надписи «Фото направления · не фото гостиницы»; подпись авторства/лицензии допустима вне изображения. Нельзя выдавать фотографию страны за фотографию конкретного отеля.

Поиск и фильтры: вылет прежде всего из Иркутска, все направления **с реально опубликованными прайс-листами**, другие города только по доступным источникам; страна/курорт/отель, даты/месяцы (включая 2027), длительность, питание, бюджет, сортировка, избранное, раскрытие всех результатов с догрузкой. Нельзя обещать весь рынок, если это ограниченный снимок. Бюджет 2 взрослых нельзя автоматически применять к другой группе.

Состав: 1–5 отдельных номеров, до 12 взрослых и 10 детей в интерфейсе; фактический возраст каждого ребёнка на дату вылета. Сохранить состав между поиском, подробностями и формой запроса. Никогда не подставлять выдуманный возраст ребёнка, не умножать «цену за двух взрослых» на количество гостей или комнат.

Активные источники в данном проекте — **Библио-Глобус и PEGAS Touristik**. PEGAS не приписывать предложения BG, самостоятельная интеграция сайта ещё не подтверждена. Для BG при отборе **подтверждённых горящих туров** требуется сначала точная метка **«ЛУЧШАЯ ЦЕНА» на выбранном маршруте**, затем оба зелёных статуса рейсов в той же строке/сеансе, потом цена/комнаты/места. Для PEGAS правило метки BG не действует. Обычный публичный список предварительных прайс-листов не надо искусственно прятать из-за отсутствия финального подтверждения; отдельный необязательный фильтр проверенных визуальных наблюдений допустим, если доказательства свежие.

## Продолжение — отображение дополнительных стран и месяцев (23.11.2026)

Задача: реальные предложения других стран должны появляться в выдаче **сразу после загрузки первого файла**, а не только когда скачаны до 13 больших разделов. Никаких несуществующих туров, чужих цен, разрешения бронирования или изменения границ 60 000 записей.

- `scripts/oracle_site_publisher.py`: `diverse_root_and_remaining` выбирает до 8 000 первых **существующих** записей циклически по стране и фактическому месяцу вылета. Сначала Таиланд, Китай, Вьетнам, затем остальные опубликованные страны. Внутри месяца приоритет свежим price-list записям с известной справочной ценой, не подменяя неизвестные цены. Остаток до 60 000 выходит в те же безопасные JSON-шарды. Каждая запись сохраняется **ровно один раз**; все поля поставщика неизменны. Наличие страны/месяца означает лишь публикацию предварительного прайс-листа, не проверку мест.
- `scripts/country-offer-balance.js`: при поиске **без выбранной страны** первые результаты чередуют реальные направления, сохраняя приоритет Таиланд → Китай → Вьетнам. Избранная пользователем сортировка «самые дешёвые по всем странам» остаётся отдельной и сознательно глобальной. Выбор страны из быстрых кнопок и бокового фильтра доступен по реально опубликованным вариантам **из выбранного города вылета**, не из чужого аэропорта.
- `scripts/catalog-shards.js`: одна недоступная или недействительная часть не скрывает остальные успешно валидированные страны из той же группы. Для каждой части предусмотрена одна повторная попытка. Если части действительно отсутствуют, интерфейс **обязан сообщить, что каталог неполный**. Детальная ссылка на тур из доступного раздела остаётся рабочей, но по неполной загрузке нельзя объявлять отсутствующий тур несуществующим.
- Тесты: `backend.test_oracle_site_publisher`, `scripts/test-catalog-shards.mjs`, `scripts/test-country-offer-balance.mjs`, `scripts/test-site.mjs` и полный Chromium smoke.

**Граница внедрения:** новая балансировка root **начнёт влиять на реальный опубликованный каталог только после того, как работающий Oracle publisher применит обновлённый Python из `main` и успешно выпустит очередной feed.** GitHub Pages CI/PASS сам по себе это не доказывает. Улучшения браузерного порядка и обработки отсутствующих шардов действуют после успешной публикации frontend main. Проверить Oracle owner-only journal и число стран, опубликованных в первых 8 000 строк; не включать неподтверждённые продажи.

### Клиентские быстрые месяцы вылета

`scripts/month-offer-filters.js` и `index.html#quickMonths`: навигация «Все даты», «Декабрь 2026», «Январь 2027» и **любые другие месяцы, реально имеющиеся в опубликованных данных**. Месяц отображается только при наличии записей из выбранного города вылета и выбранной страны; у несуществующего месяца нет фиктивного счётчика. По клику заполняются точные границы календарного месяца в полях дат и вызывается настоящий поиск. Пользовательский диапазон произвольных дат не маскируется под «Все даты». На мобильном месяцы доступны через горизонтальную прокрутку, без чрезмерного списка на экране. Реальная цена/два рейса/статус бронирования по-прежнему требуют авторизованной проверки, включать оплаты нельзя.

Тест: `node scripts/test-month-offer-filters.mjs` (включён в CI). Проверяет декабрь 2026 и 2027, високосный февраль 2028, неверные даты и привязку к стране/городу.

Даже подписанный «Пейзаж: …» является неподходящей визуализацией в карточке конкретного отеля: покупатель может принять его за гостиницу.

**Исправлено в \`index.html\`:** полностью отключён fallback картинок направления \`renderDestinationPhoto\` для всех туров. На фото карточки допускаются только изображения с идентификатором того же hotel_id, названием гостиницы, страной и документально ограниченным источником/правами. Выбранный снимок получает DOM-маркеры \`data-hotel-id\` и \`data-media-evidence=EXACT_PROPERTY_LICENSED\`, которые использует браузерный CI. Если подтверждённой фотографии нет или все ссылки не открываются, остаётся аккуратный фирменный нефотографический блок JAMAICA. **Никогда не подставлять красивый пейзаж, фотографию другой гостиницы или картинку из произвольного поисковика.** Файл \`assets/jamaica-destination-media.json\` как справочник лицензированных пейзажей сохранён, но использовать его для \`tourResultCard\` запрещено.

**Все опубликованные туры:** \`scripts/catalog_property_identity.py\` делает полное сопоставление **каждой** записи из root плюс всех 13 шардов (до 60 000) с независимым справочником Библио-Глобуса: hotel ID, нормализованное точное название, страна, Иркутск, уникальный preview ID и запрет ложных \`bookable\`/\`flight_verified\`. Нельзя считать совпадением похожее название, другой отель того же бренда или правильную страну с неверным ID. \`scripts/site_no_node_qa.py\` и \`scripts/local_site_qa.py\` блокируют CI, если обнаружено любое несоответствие. \`scripts/oracle_site_publisher.py\` вызывает ту же проверку **до записи и публикации**: при ошибке отказывается публиковать новый каталог вместо публикации неправильной карточки. Правило начинает работать на Oracle **после фактического обновления серверного Python-скрипта**, которое нельзя считать выполненным только по GitHub Pages.

Важно: отсутствие лицензированной **фотографии гостиницы** означает отсутствие снимка на карточке, **не удаление подлинной записи о туре**. Иначе почти все реальные направления пропадут, потому что действующих одобренных CDN-фотографий ещё нет. Если **сама запись** не совпадает с официальным справочником по отелю — **она не должна попасть в новую публикацию**. Фото с метаданными, но без фактической визуальной/договорной проверки содержания не считаются достоверными только потому, что файл или подпись содержат название отеля.

Проверка:
\`\`\`bash
python3 -B scripts/local_site_qa.py
python3 -B scripts/site_no_node_qa.py
python3 -B -m unittest -v backend.test_catalog_property_identity
node scripts/test-site.mjs
python3 -B scripts/browser_smoke_playwright.py
\`\`\`

Нельзя путать «все записи соответствуют справочнику отелей» с «рейсы, номера, окончательная стоимость и право продажи подтверждены» — для последних нужны независимые supplier preflight, соглашения и живой booking/PSP API. До их получения не открывать оплату.

## P0 — строго только «ЛУЧШАЯ ЦЕНА» и ДВА зелёных самолётика (23.11.2026)

**Новое жёсткое требование пользователя**: ВСЕ публичные карточки туров, независимо от страны, отеля, месяца, количества ночей и сортировки, публикуются **только** при одновременном наличии:
1. Бот обнаружил официальную метку Библио-Глобуса **«ЛУЧШАЯ ЦЕНА»** на конкретной строке маршрута и **сначала выбрал эту строку**.
2. В открытой из этой же строки карточке конкретного отеля/номера/даты бот обнаружил **зелёный статус перелёта ТУДА**.
3. В той же подтверждённой карточке бот обнаружил **зелёный статус перелёта ОБРАТНО**; рейсы, price-list ID, browser-session digest, hotel ID, дата и тип номера должны быть связаны с той же строкой.

Доверенный приватный \`backend/bg_route_first_visual_gate.py\` проверяет порядок, source IDs, session ID и срок до 15 минут. Публичный \`tour-visual-evidence.json\` проходит \`JamaicaVisualSelection.read\`. Наличие обычного прайс-листа, справочной цены, двух нарисованных самолётиков, той же страны, похожей гостиницы или рекламной метки без последующего выбора маршрута **НЕ достаточны**.

**Изменено:**
- \`scripts/public-visual-policy.js\`: общий обязательный проверяющий механизм для публичного браузера, \`eligible\` и \`filter\`. Нет обхода через чекбокс, сортировку по дешёвой цене, избранное, разные месяцы или другую страну. Пропавшее, чужое, просроченное, невалидное доказательство означает **HIDE**.
- \`index.html\`: выдача, число найденных, быстрые страны и месяцы работают **только по прошедшим проверку записям**. Старый необязательный фильтр превращён в фиксированное правило. При нуле подтверждений выводится сообщение без единой карточки, не показываются 60 000 исходных прайс-листов. Официальный подтверждённый offer также не публикуется без лучшей цены и двух зелёных рейсов.
- \`preview.html\`, \`quote.html\`, \`hotel.html\`: прямые ссылки, расчёт, предложения других стран и поездки в карточке гостиницы не должны обходить тот же строгий фильтр. Кнопка расчёта повторно проверяет свежесть доказательства.
- \`tour.html\`, \`checkout.html\`: удалён путь \`STANDARD_TWO_FLIGHTS\`, не имеющий свидетельства «ЛУЧШАЯ ЦЕНА». По текущему правилу такой тур не может быть показан/продан как удовлетворяющий требованиям.
- \`route.html\`: старый справочный route-list не обладает точной связью с подтверждённым source route ID; прямой URL не показывает неподтверждённые туры/отели/маршрутные карточки.
- \`scripts/public_tour_eligibility.py\`: **серверный фильтр** публикует в \`tour-previews.json\` и \`tour-previews-shards/*\` только записи с совпавшим \`preview_id\` валидированного свежего доказательства бота. Остальные внутренние сканы и приватный \`recent-price-list-previews.json\` продолжают работать, но публично не публикуются. Если proof feed пуст — **публичный каталог с 0 карточек и 0 шардов является корректным**. Удаляются устаревшие публичные shard-файлы при успешном обновлении Oracle. Запрещено возвращать старые 60 000 ради маркетингового «наполнения».
- \`scripts/site_no_node_qa.py\`, \`scripts/local_site_qa.py\`: валидируют строгую публикацию, включая легитимный нуль. \`scripts/test-strict-public-visual-policy.mjs\`, \`backend/test_public_tour_eligibility.py\` и браузерный тест проверяют запрет чужих, просроченных и непроверенных вариантов.

**Текущий факт:** в \`tour-visual-evidence.json\` по состоянию на аудит \`entries: []\`, в \`verified-offers.json\` — \`offers: []\`. Следовательно, строгая живая выдача сейчас ОБЯЗАНА содержать **0 туров**. Это не означает, что оператор не продаёт туров; это значит, что бот ещё не доставил ни одного доказательства в новый строгий формат. Для реально работающей продажи необходимо привязать имеющийся runtime бота V190 к owner-only receipt adapter и наладить независимую проверку цены, мест, договора и PSP. **Не включать оплату** только на основании визуального доказательства.

**Граница деплоя:** фронтенд-фильтр применяется после GitHub Pages, независимо от старой версии Oracle. Но удаление не прошедших проверку строк **из самого публичного GitHub JSON** начнётся лишь после обновления системного процесса \`jamaica-oracle-catalog-5min\` на Oracle до новой версии \`scripts/oracle_site_publisher.py\`. До подтверждения этого необходимо честно считать, что старые исходные JSON остаются публично доступны напрямую, хотя карточки на экране не показываются. Никаких таймеров бота менять нельзя.

## P0 handoff — почему сейчас пустая выдача и как восстановить продажи без ложных туров

После строгого правила 23.11.2026 сайт JAMAICA видимо показывает **0 карточек**, потому что \`tour-visual-evidence.json\` не содержит подтверждённых событий (проверено на GitHub). В открытом репозитории в то же время могут продолжать лежать **десятки тысяч исходных предварительных записей** от старого Oracle publisher. Эти записи имеют \`bookable=false\`, не являются турпродуктом к продаже и **НЕ ДОЛЖНЫ** по умолчанию появляться как карточки. Ноль подтверждений НЕ означает отсутствия туров у оператора.

**Что сделано в этой ветке:**

- \`scripts/source-coverage.js\`, \`index.html#sourceSearchCoverage\`, CSS: при нуле карточек показывается **отдельная нефинансовая панель наблюдаемых стран и месяцев сканирования**. Числа — сырые записи из \`countries_status\` или нового \`search_coverage\`. Панель не содержит названий отелей, цен, кнопок оплаты, «ЛУЧШАЯ ЦЕНА» или статуса мест и никоим образом не участвует в \`verifiedRows()\`. После применения нового Oracle publisher, который правильно публикует 0 туров, \`scripts/public_tour_eligibility.py\` сохраняет лишь этот безопасный агрегированный обзор \`search_coverage.classification=SOURCE_SCAN_ONLY_NOT_OFFERS\`, чтобы география поиска не исчезала.
- \`scripts/diagnose_live_visual_link_from_lenovo.sh\`: **read-only** аудит одного реального сервера из Lenovo: активность таймеров сайта/бота, версия фактического исполняемого издателя в Oracle, статус и число приватных receipts, число публичных визуальных совпадений и карточек. **Никаких секретов, URL, сессий, бронирований, логинов и необработанных записей не печатает**. Запускать в локальном клоне репозитория на Lenovo:

  \`\`\`bash
  bash scripts/diagnose_live_visual_link_from_lenovo.sh
  \`\`\`

- \`scripts/upgrade_oracle_catalog_on_server_once.sh\`: усилен **предварительной проверкой существования strict visual gate** и **контрольной сверкой каждой публичной карточки с полученными доказательствами после первого реального запуска сервиса**. Издатель не считается обновлённым, если только успешно компилируется или если \`systemctl\` запущен, но в public catalog осталось 60 000 неподтверждённых вариантов. При ошибке исполняемый скрипт откатывается, таймер восстанавливается. **Не трогает частоту или исходный код BG/PEGAS/Telegram-бота**. Запускать с Lenovo после проверки контроля версий и состояний:

  \`\`\`bash
  bash scripts/upgrade_oracle_catalog_on_server_once.sh
  \`\`\`

- \`scripts/trusted_bot_receipt_sink.py\`: OWNER-ONLY API **внутри** доверенного браузерного процесса BG. После реального выбора строки маршрута с \`ЛУЧШАЯ ЦЕНА\` и инспекции обеих зелёных иконок этот процесс должен передать непосредственно в \`save_from_trusted_browser(route,flight,preview)\` объекты из **одной** авторизованной сессии; \`backend.bg_route_first_visual_gate.route_first_pair_matches\` сверяет exact preview ID, origin Иркутск, дату, отель, комнату, количество ночей, route/list/source IDs, порядок события и тайминги. Только при PASS атомарная запись \`0600\` в \`~/.local/share/jamaica-oracle-catalog/private-bg-route-first-receipts.json\`. Не импортировать любые значения из Telegram-текстов, старых копий прайс-листов, скриншотов незнакомых страниц или пользовательских URL. Это **НЕ запущенная интеграция бота**, а безопасный контракт; до модификации реального V190/V193 браузера receipts останутся пустыми. Нельзя считать, что бот обновлён только после GitHub merge или успешного сайта.
- Проверки JS/Python включены в CI: нулевые подтверждённые туры не приводят к публикации старых карточек, география поиска сохраняется, writer отклоняет отсутствие метки, любой незелёный рейс, другие IDs, старую сессию и посторонние секретные поля.

**Что требуется для реальных карточек:** приватный бот Oracle/Lenovo должен действительно вызвать безопасный writer в **точке завершённого живого браузерного прохода**, на той же машине и под тем же пользователем \`ubuntu\`, который владеет файлом; или нужен отдельный аутентифицированный защищённый канал, которого ещё нет. Только после положительного результата аудита можно считать pipeline \`bot → receipts → publisher → public proof → exact card\` законченным. Для полноценной продажи затем отдельно нужны API цены на реальный состав и живые места, договор/юридические права и PSP; зелёные иконки сами по себе не разрешают платёж.

**Предупреждение по миграции:** в старом GitHub feed всё ещё может лежать 60 000 предварительных JSON-строк, поскольку действие GitHub Pages НЕ обновляет исполняемый publisher Oracle. До выполнения безопасного upgrade и нового полного прогона нельзя считать старый public source удалённым.
