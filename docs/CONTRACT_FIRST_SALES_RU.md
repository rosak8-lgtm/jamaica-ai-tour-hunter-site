# JAMAICA — утверждённая модель контракт → платёж → бронь

Версия 20.11.2026. Это техническая спецификация и реализованная **доменная логика с тестовыми адаптерами**, а не запущенный приём денег. Внешние API, юридические шаблоны и серверная авторизация пока не подключены.

## Порядок: принципиально не переставлять этапы

1. Клиент выбирает страну, гостиницу, дату, ночи, тип номера из каталога JAMAICA `preview.html`. Поставщик не показывается в маркетинговой выдаче; сведения, требуемые договором, должны быть раскрыты.
2. `quote.html` / `POST /v1/preview-quotes`: **READ-ONLY проверка №1** — новая сумма на выбранный состав туристов, рейсы туда/обратно, статус `IN_STOCK` или `ON_REQUEST`, `hotel_stop=false`, валюта RUB. Предварительную сумму нельзя подменять результатом. Для `ON_REQUEST` требуется явное согласие.
3. `checkout.html?quote=<private-offer-id>`: покупатель видит новую сумму, юридического продавца, условия, свой заказ и принимает условия. `POST /v1/contract-orders/draft` создаёт **договор**, а не бронь или платёж. `backend/contract_first_order_engine.py:draft_contract`.
4. `account.html` предлагает внешнюю проверяемую электронную подпись. `POST /v1/contract-orders/<id>/verify-signature` перепроверяет подпись и хэш договора непосредственно у провайдера — клик «подписал» не считается доказательством.
5. **READ-ONLY проверка №2** выполняется после подтверждённой подписи и **до** создания PSP-платежа через `POST /v1/contract-orders/<id>/payment`. Цена должна точно совпасть с подписанным договором, рейсы и гостиница должны пройти повторную проверку. Иначе оплаты нет.
6. Независимый серверный webhook PSP и запрос к провайдеру подтверждают **поступление денег**, а не только возврат браузера.
7. **READ-ONLY проверка №3** после поступления денег и **до первой попытки создать заявку у туроператора**. Снова сравнить полную сумму подписанного договора, состав, туда/обратно, отель и стоп-продажу. При расхождении — `REFUND_REQUIRED` и никакой заявки.
8. **Только теперь** вызвать идемпотентный `supplier.create_booking(order,order_id)` от имени авторизованного агентского кабинета. Статус `CONFIRMED` переводит заказ в `BOOKED`; `ON_REQUEST` — только в `SUPPLIER_ON_REQUEST`, где номер ещё не подтверждён.
9. После настоящего подтверждения брони создаётся приватное событие `TOUR_BOOKED`; при `ON_REQUEST` — **другое** событие `TOUR_REQUESTED_WAITING_HOTEL`. Telegram worker `backend/send_booking_notifications.py` использует закрытые `JAMAICA_TELEGRAM_BOT_TOKEN` и `JAMAICA_TELEGRAM_OWNER_CHAT_ID`.

## Обязательные состояния

`CONTRACT_CREATING` → `AWAITING_SIGNATURE` → `CONTRACT_SIGNED` → `PAYMENT_CREATING` → `PAYMENT_PENDING` → `PAID_RECHECK_REQUIRED` → `BOOKING_IN_PROGRESS` → `BOOKED` или `SUPPLIER_ON_REQUEST`.

Отказы и неопределённости: `CONTRACT_FAILED`, `PAYMENT_FAILED`, `PAYMENT_REVIEW_REQUIRED`, `BOOKING_RECONCILIATION_REQUIRED`, `REFUND_REQUIRED`, `REFUND_PENDING`, `REFUNDED`.

Нельзя запускать повторное создание заявки после тайм-аута: заявка могла быть создана до обрыва сети. Запрос `lookup_booking(order_id)` через API должен сначала сверить статус у поставщика. Пока ответ неопределённый, статус `BOOKING_RECONCILIATION_REQUIRED`; не создавать дубликат, не объявлять успех и не инициировать необоснованный возврат.

При `ON_REQUEST` после создания заявки нужно периодически проверять ответ гостиницы. Только `CONFIRMED` даёт уведомление «забронирован»; авторитетный отказ — уведомление и возврат по условиям договора.

## Контракт серверного API

Все эндпоинты требуют аутентификации покупателя, авторизации доступа к конкретному заказу, TLS, защиты от повторных запросов и корректных заголовков CORS/CSRF. `buyer_id` сервер берёт из проверенной сессии, а не из тела браузера. Внешний HTTP API **пока не создан и не размещён**.

| HTTP | Маршрут | Назначение |
|---|---|---|
| POST | `/v1/preview-quotes` | READ-ONLY котировка №1 по выбранному `preview_id`, составу и согласию `ON_REQUEST` |
| GET | `/v1/private-quotes/<quote_id>` | Приватная свежая подтверждённая котировка только её покупателю |
| POST | `/v1/contract-orders/draft` | Создать договор, получить ссылку на подписание, НЕ платёж |
| GET | `/v1/contract-orders/<id>` | Текущий статус в личном кабинете |
| POST | `/v1/contract-orders/<id>/verify-signature` | Серверная проверка подписи |
| POST | `/v1/contract-orders/<id>/payment` | Котировка №2, затем платёжная сессия PSP |
| POST | `/v1/payment-webhooks/<provider>` | Проверка подписи PSP webhook, независимое получение статуса денег, котировка №3, заявка |
| GET/POST | Внутренние worker-эндпоинты | Сверка поставщика, возврат, outbox уведомлений |

Клиент никогда не отправляет `<confirm/>` напрямую. Только приватный агентский сервер использует разрешённый endpoint создания заявки. Не хранить паспортные сведения или реквизиты карт в журнале.

## Реализованные части в репозитории

- `backend/preview_quote_engine.py` — строгое сопоставление опубликованного предварительного варианта с приватной котировкой, без брони.
- `backend/contract_first_order_engine.py` — договор/подпись, три проверки, PSP, создание заявки только после денег, обработка неопределённости, возвратов и `ON_REQUEST`.
- `backend/sqlite_order_repository.py` — локальная приватная SQLite для котировок, заказов, атомарных изменений состояния и outbox.
- `backend/send_booking_notifications.py` — приватная отправка Telegram после создания события outbox.
- `preview.html`, `quote.html`, `checkout.html`, `account.html` — клиентский путь, пока **закрытый конфигурационными флагами**.
