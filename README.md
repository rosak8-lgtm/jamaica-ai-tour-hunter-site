# JAMAICA — поиск путешествий и подготовка онлайн-бронирования

Сайт JAMAICA для поиска вариантов путешествий из Иркутска по нескольким странам. Репозиторий содержит клиентскую витрину, справочник гостиниц, реальные **справочные** варианты дат/номеров из авторизованных прайс-листов, тесты и закрытые по умолчанию механизмы оформления.

## Текущее состояние (20 ноября 2026)

Последний успешный импорт на Oracle: **4 062 предварительных варианта, из них 3 641 с ориентировочной суммой за двух взрослых** по Таиланду, Индонезии, России, Турции и Шри-Ланке, 3 630 маршрутных записей, 11 046 гостиниц в справочнике. После обновления источника цифры меняются. **Ни один предварительный вариант не равен подтвержденному бронированию.**

Сайт показывает другие страны в той же выдаче, поддерживает уточнение страны, дат, отеля и продолжительности, ведёт на подробную карточку выбранной поездки. Отсутствие известной цены не должно полностью скрывать варианты: бюджет для таких карточек требует проверки. Ориентир в рублях для пары взрослых отображается только когда прайс подтверждает валюту и состав: первые 30 минут как свежая справочная сумма, затем с предупреждением об устаревании и отметкой времени — максимум до 24 часов после импорта. Это не финальная цена, а покупка требует новой серверной котировки.

Платёжная и броневая функциональность **не включена**: `checkout-config.json` содержит `live_booking_enabled=false` и `payments_enabled=false`. Справочник 251 страны не означает, что из Иркутска на каждую есть туры. Названия поставщиков не используются в рекламном интерфейсе, но юридически обязательные сведения о продавце и туроператоре должны быть доступны при заключении договора.

## Lenovo — проверка без Node.js

```bash
cd "$HOME/Загрузки/JAMAICA_WEB_LIVE_BRIDGE_20261120"
git pull --ff-only
bash scripts/verify_site_from_lenovo.sh
```

Скрипт всегда запускает две Python-проверки. Если `node` доступен, выполняет также `scripts/test-site.mjs`; иначе явно пишет, что JavaScript VM-тесты пропущены на Lenovo и выполняются в GitHub Actions. Если доступен Python Playwright с Chromium, выполняется реальный локальный тест: поиск вариантов разных стран → фильтр Турция → выбранный тур → отсутствие активной оплаты.

## Oracle — безопасная проверка необходимых полей API бронирования

```bash
bash scripts/audit_booking_fields_from_lenovo.sh
```

Проверяет только наличие исходных служебных параметров прайса для официального расчёта заявки на трёх будущих направлениях. Не отправляет POST, не формирует заявку, не проверяет паспорта, не принимает оплату и не публикует секреты. Отсутствие одного поля показывает причину технической блокировки, а наличие всех полей **не является разрешением бронировать**.

Полный процесс продажи: авторизованная серверная котировка на указанных туристов → проверка мест и обоих перелётов → согласие с договором и данными юридического продавца → разрешённая бронь через API → PSP с надёжными вебхуками и статусом → документы. Для включения нужны права агентства на создание заявок, реальные юридические реквизиты, платёжный провайдер и рабочие приватные серверные адаптеры. Не включать флаги в конфигурации вручную.

Расширенные материалы: [docs/LIVE_SOURCE_INTEGRATION_RU.md](docs/LIVE_SOURCE_INTEGRATION_RU.md).

## Новый утверждённый порядок продаж: договор → оплата → бронь

**Требование владельца от 20.11.2026:** цена и доступность проверяются три раза: перед договором, после проверенной подписи перед оплатой, после поступления денег перед заявкой. Гостиница может иметь статус «в наличии» или «под запрос» с явным согласием. Только после оплаты и третьей проверки можно создавать заявку в агентском ЛК. При подтверждении туроператором владелец получает отдельное уведомление.

Серверные компоненты с тестовыми адаптерами: `backend/preview_quote_engine.py` (из публичного варианта в приватную котировку), `backend/contract_first_order_engine.py` (подпись → платёж → третья проверка → бронь), `backend/sqlite_order_repository.py` (атомарные статусы и очередь), `backend/send_booking_notifications.py` (уведомления с приватным токеном). Клиентские страницы: `preview.html` → `quote.html` → `checkout.html` → `account.html`.

**Важно:** это реализованная и тестируемая логика с интерфейсами внешних сервисов, **не действующая касса**. Настройки подписи, авторизации, оплаты и реальной брони остаются `false`. Нельзя просто включить флаги без юридического договора, PSP, подтверждённого API агента, подписанной интеграции ЭП и безопасного backend-сервера.

[Подробная последовательность и контракты API](docs/CONTRACT_FIRST_SALES_RU.md).

## Подтверждённые сквозные проверки (20.11.2026)

GitHub Actions успешно выполнил **130 Python unit-тестов**, проверки JavaScript и реальный браузерный smoke-тест в Chromium: на первой странице видны **5 разных стран**, работает фильтр «Турция», выбранная карточка ведёт в подробности и далее к странице нового расчёта; личный кабинет корректно блокирует неподключённую оплату. Проверка не включает настоящую оплату или создание заявки оператору. Публичный импорт теперь допускает проверку до 13 потенциальных направлений по прайс-листам, но не придумывает туры по странам без подтверждённого источника.

`backend/bg_tour_api_xml.py` — защищённый внутренний строитель официального XML запроса цены (без `<confirm/>`) и отдельного запроса заявки после оплаты. При обработке ответов полной ценой для туриста является `fullamount`, а не `amount` после комиссии. Создание заявки не считается окончательным бронированием до независимого подтверждения статуса оператором. Используется состояние `SUPPLIER_SUBMITTED`.
