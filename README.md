## Исправление гостиничных фотографий — запрет подмены пейзажами

Важное исправление: **в поисковой карточке и галерее гостиницы теперь могут отображаться только фотографии именно выбранного отеля**, привязанные к его ID и подтверждённым коммерческим правам на показ. Предыдущие автоматические «фото страны», пляжей, городских панорам, устаревшие виды из гостиницы и поиск изображений по совпадению названия как способ наполнения отелей **удалены**. Если фотографии гостиницы нет, отображается аккуратная заглушка «Проверенная фотография гостиницы пока недоступна» без чужих снимков.

Поддерживаются два независимых источника:
- Кураторский реестр `hotel-enrichment.json`: только идентифицированные фотографии фасада или общественных помещений (`hotel_exterior`, `hotel_public_area`), с URL Wikimedia Commons, указанием автора и лицензии. Виды города и исторические виды могут храниться в метаданных, но не выдаются за фотографии отеля.
- Договорно разрешённые внешние CDN из `hotel-media-approved.json`: точный ID/название/страна, подтверждённое коммерческое разрешение, привязка доменов и HTTPS, срок и источник прав. Фото не загружаются и не копируются на Oracle; их браузер получает напрямую.

**Причина пустых изображений:** текущая база разрешённых фото охватывает лишь отдельные отели. Система не может законно и достоверно заполнить десятки тысяч карточек фотографиями с произвольных OTA-сайтов без гостиничного лицензированного фотофида. Показ фальшивого фото вместо честной заглушки запрещён.

## Фотографии непосредственно в результатах поиска (21.11.2026)

Теперь карточки конкретных поездок могут показывать внешний снимок без хранения изображения на Oracle:

- **Сначала фото настоящего отеля**, если его ID, точное название и страна совпадают с `hotel-enrichment.json`, файл расположен на Wikimedia Commons, тип фотографии и свободная лицензия проверены.
- **Если фото именно отеля не подтверждено**, может отображаться иллюстрация страны из Wikimedia Commons с отдельной подписью `НЕ фото отеля`. Браузер проверяет адреса HTTPS, домен источника, допустимую коммерческую лицензию и автора; ссылки на оригинал и лицензию сохраняются.
- **Если источник недоступен, отсутствуют права или автор не указан**, вместо битого изображения показывается оформленная заглушка. По стране выполняется не более одного запроса поиска изображений на страницу браузера (повторное использование через кеш промисов). Изображения запрашивает браузер туриста напрямую с Commons.
- Данные поставщиков, Booking, Tripadvisor и другие изображения с неустановленным разрешением не публикуются автоматически.

Фото направления **не** являются фотографиями выбранных гостиниц. Фотогалереи каждого отеля, договор, оплата и разрешённая бронь — отдельные функции. Загрузка фото не делает предварительный тур доступным для покупки.

## Исправление пропуска дальних дат при лимите 2 800 строк на страну (21.11.2026)

После расширения помесячного поиска обнаружен второй дефект: старый код занимал весь лимит первыми 2 800 строками **первого прайс-листа страны** и переставал добавлять варианты из последующих прайс-листов, даже если их успешно скачал и проверил. Это не ошибка API, а неправильный выбор опубликованных кандидатов.

Теперь для каждого из максимум пяти проверяемых прайс-листов собирается отдельная ограниченная выборка, затем кандидаты объединяются, и только после этого отбираются максимум 2 800 на страну с учётом разных дат и меньших известных справочных цен. Ограничение общего публичного JSON 8 000 сохранено для безопасности и производительности. `total_candidate_previews` и `truncated_to_public_limit` учитывают также отсечённые на уровне страны варианты, чтобы сайт не показывал ложное «полное покрытие».

Это **не** отменяет ограничений прайс-листов, не гарантирует уникальные страны, не создаёт подтверждённые цены и не расширяет коммерческие права на фотографии. Преимущество — отсутствие систематического пропуска дальних дат только из-за большой первой выгрузки.

## Новый утверждённый порядок продаж: договор → оплата → бронь

**Требование владельца от 20.11.2026:** цена и доступность проверяются три раза: перед договором, после проверенной подписи перед оплатой, после поступления денег перед заявкой. Гостиница может иметь статус «в наличии» или «под запрос» с явным согласием. Только после оплаты и третьей проверки можно создавать заявку в агентском ЛК. При подтверждении туроператором владелец получает отдельное уведомление.

Серверные компоненты с тестовыми адаптерами: `backend/preview_quote_engine.py` (из публичного варианта в приватную котировку), `backend/contract_first_order_engine.py` (подпись → платёж → третья проверка → бронь), `backend/sqlite_order_repository.py` (атомарные статусы и очередь), `backend/send_booking_notifications.py` (уведомления с приватным токеном). Клиентские страницы: `preview.html` → `quote.html` → `checkout.html` → `account.html`.

**Важно:** это реализованная и тестируемая логика с интерфейсами внешних сервисов, **не действующая касса**. Настройки подписи, авторизации, оплаты и реальной брони остаются `false`. Нельзя просто включить флаги без юридического договора, PSP, подтверждённого API агента, подписанной интеграции ЭП и безопасного backend-сервера.

[Подробная последовательность и контракты API](docs/CONTRACT_FIRST_SALES_RU.md).

## Расширенный каталог и безопасность личных кабинетов

По последнему запуску Lenovo (20.11.2026) опубликовано 4 081 предварительное предложение по 5 странам, из них 3 669 с ориентиром в рублях на **двух взрослых**. Новый экспорт проверяет до **13 направлений**, до **трёх различных дат прайс-листов** на направление, с безопасным ограничением **8 000 записей**. Это максимум импорта, а не обещанное число доступных туров: фактическое количество определяется текущим API.

**Исправление состава туристов:** выбранные в поиске взрослые и дети теперь передаются в выбранную карточку и на страницу официального расчёта. Стоимость «2 взрослых» не применяется к одиночным туристам или семьям. Пока доверенная котировка реализована только для двух взрослых без детей, прочие составы блокируются с явным сообщением, а не получают фиктивную цену.

**Защита личного кабинета:** серверные котировки привязаны к buyer_id, который получает приватный сервер после проверки сессии. Нельзя создать договор по чужой котировке. SQLite предлагает отдельные методы get_offer_for_buyer и get_order_for_buyer, но публичный HTTP API авторизации пока не размещён.

**Первый официальный расчёт без создания заявки:** модуль backend/bg_read_only_price_client.py умеет формировать и отправлять **только запрос цены** через официальный HTTPS zayavkaapi, когда запущен на частном сервере с разрешёнными агентскими доступами и данными туристов. Он запрещает <confirm/>, перенаправления и посторонние хосты. **В Oracle боевые вызовы не выполнялись**, поскольку права на API создания заявок, безопасный сбор паспортных данных и авторизованные сессии покупателей пока не подтверждены. Указанная цена сама по себе не доказывает наличие перелётов и мест.

Подробности протокола: https://www.bgoperator.ru/texts/api/tour-api.html. Для электронного оформления могут потребоваться личные данные пассажиров и заказчика; их нельзя публиковать в GitHub, передавать в URL, сохранять в браузерном localStorage или записывать в открытые логи.

**Готовая для проверки модель ≠ действующий магазин.** Боевая продажа зависит от проверки доступности рейсов и квот, юридического продавца и договора, доказуемой электронной подписи, реального PSP, подписанных серверных webhook, авторизованной отправки заявки и её независимого подтверждения туроператором. Все платёжные и броневые переключатели остаются выключенными.

## Точность рублёвой цены, два зелёных самолётика и частота обновления (20.11.2026)

Последний запуск Lenovo опубликовал **6 180** комбинаций отель/номер/дата для пяти стран с вылетом из Иркутска; **5 383** имеют официальную цену в RUB по прайс-листу на пару взрослых. Такая цифра является **ценой на момент выгрузки**, а не вычисленной приблизительной суммой. Она не фиксирует цену до оплаты и не доказывает наличие свободных мест на обоих рейсах после обновления.

В документации Библио-Глобуса (`https://export.bgoperator.ru/`) поле `tourComposition` (`xml=31`) описывает рейсы с направлением `n=0` (туда), `n=1` (обратно) и индикатором `q`: первый символ — места в экономклассе; `1..9`, `a`, `r` означают наличие на момент ответа, `0` требует запроса, `c` — нет мест. Текст `flights` в HTML без проверяемой структуры не даёт права объявлять два самолётика зелёными. Добавлены `scripts/flight_availability_evidence.py`, тесты и **безопасный агрегированный аудит** с Oracle через `bash scripts/check_green_flights_from_lenovo.sh`. Реальный результат аудита нужен до отображения зелёных значков на сайте. Наличие зелёных в момент выгрузки не отменяет три проверки до/после оплаты.

В справочнике 251 страна, но туры из Иркутска могут быть опубликованы только по направлениям, для которых официальная выгрузка содержит соответствующий город отправления и будущие прайс-листы. В текущем наборе 12 подходящих каталожных стран, по пяти есть реальные строки. Импортёр теперь перебирает **все** страны справочника, удовлетворяющие этим критериям, без искусственного обрыва на первых 13; прочие страны остаются доступными для справочного поиска, но не выдаются за реальные доступные туры.

**Ранее:** импорт каталога выполнялся вручную из Lenovo командой синхронизации, а страница загружала `tour-previews.json` только при открытии; таймера автоматической публикации не было в этом репозитории. **После изменений:** открытая страница перечитывает каталог каждые **5 минут** и после возвращения на вкладку. Источник также опрашивает Oracle каждые **5 минут** — после однократного развёртывания серверного таймера `jamaica-oracle-catalog-5min.timer`. Активный старый таймер `jamaica-tour-catalog-refresh.timer` на Lenovo отключается автоматически только после успешного первого запуска на сервере. При выключенном Lenovo сервер продолжает импорт.

**Важно:** таймер обновляет только каталог. Живой запрос окончательной цены и проверку гостиницы/рейсов перед договором, перед оплатой и после оплаты будут выполнять приватные API-адаптеры после подключения и разрешения. Платёж и бронь до тех пор заблокированы.

## Разблокировка поиска по остальным странам (21.11.2026)

Справочник JAMAICA содержит 251 страну. В текущем публичном справочнике 91 страна имеет флаг туроператорского каталога; для **12** указана возможность поиска из Иркутска, а в последнем импортированном прайс-листе конкретные туры подтверждены лишь по **пяти**. Это важное различие: страна в списке ≠ тур по выбранному вылету ≠ свободное место на рейсе ≠ подтверждённое бронирование.

**Исправлено ограничение кода:** теперь `scripts/oracle_bg_preview_export.py` каждые 5 минут проверяет все 12 основных направлений **и** Китай, Вьетнам плюс восемь других стран из общего туроператорского каталога по ротации. Остальные страны с туроператорским каталогом проходят проверку в последующих циклах; весь дополнительный список покрывается приблизительно за час при успешной работе сервера. Если API действительно даёт будущий прайс-лист **с вылетом из Иркутска** для дополнительной страны, страна добавляется в закрытое состояние Oracle и далее проверяется при каждом запуске. Нельзя выдавать гостиничный справочник за источник подтверждённых туров.

За один цикл теперь проверяется до **пяти разных будущих дат прайс-листа** по каждой выбранной стране, вместо трёх. При переполнении общего публичного ограничения в **8 000 реальных вариантов** записи распределяются между странами справедливо: первыми большим объёмом нельзя скрыть последующие страны. Это ещё не загрузка всех комбинаций за все 180 дней — потребуется разделение каталога на страницы и подтверждённый доступ к другим источникам, в частности PEGAS Touristik. Сейчас PEGAS **не интегрирован в серверный импорт сайта**, и нельзя приписывать его туры единственному работающему источнику.

**На сайте:** в блоке результатов поиска доступен выбор **любой из 251 стран**, в том числе Египта, ОАЭ, Китая, Вьетнама и Мальдив. Если нет проверенных цен и дат из Иркутска, сайт прямо сообщает об отсутствии подтверждённых вариантов, а не подменяет их вымышленными. Новые дополнительные направления появляются автоматически после фактического получения данных.

**Запуск расширенного импорта на уже работающем Oracle:** `git pull --ff-only` в локальном checkout и однократно `bash scripts/upgrade_oracle_catalog_on_server_once.sh` с установленного SSH-клиента. Старый пятиминутный таймер при этом сохраняется. Далее Oracle получает изменения экспортёра напрямую из GitHub и Lenovo больше не участвует в регулярном процессе.
