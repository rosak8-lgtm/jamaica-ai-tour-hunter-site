# JAMAICA: точный состав туристов и расчёт поставщика (2026-11-22)

## Проблема
Публичная выгрузка `tour-previews.json` содержит **предварительные записи прайс-листов**, в которых `price_reference_party="TWO_ADULTS"`, а `bookable=false`, `quote_verified=false`, `availability_verified=false`. Это **не** тариф для одного взрослого, семьи, двух номеров или группы. Простое деление/умножение таких цен запрещено.

## Как состав передаётся в JAMAICA
В пользовательском поиске создаются от 1 до 5 групп (каждая группа — проживающие в одном номере). Указывается число взрослых (суммарно до 12), детей (суммарно до 10), **возраст каждого ребёнка на дату начала тура** (0–17). Никаких предполагаемых возрастов по умолчанию. Количество взрослых должно быть не менее 1 в каждой группе; это ограничение текущего **интерфейса JAMAICA**, а не заявление об универсальных правилах всех операторов.

Схема JS: `[{adults:2,child_ages:[6,12]},{adults:1,child_ages:[4]}]`.
Каноническая запись без ФИО и дат рождения: `2:6,12|1:4`. Код передаёт только выбранные числа в параметрах URL `rooms`, `adults` и `kids`, сверяя их между собой. Функция `JamaicaTravelers.fromQuery` отбрасывает несовпадающие параметры и некорректные возраста. После выбора тура состав отображается в подробностях и на странице проверки котировки.

Общие гостиничные записи остаются доступными при изменении состава, но для любого состава **кроме одного номера с двумя взрослыми** прайс-цена отключена, а статус наличия номера остаётся неподтверждённым. Даже для двух взрослых из разных номеров она не переносится. Оплата не включается.

## Официальная модель Библио-Глобуса и требования к интеграции
Проверенные документы:
- https://www.bgoperator.ru/docs.shtml?action=info&section=howto_groups — группа = проживание вместе в номере, разные группы для разных номеров, возраст детей на дату начала тура
- https://www.bgoperator.ru/texts/load-xml-prices.html — параметр `p` описывает группы и даты рождения, отдельные прайсы с диапазонами возрастов `prices/ag`
- https://export.bgoperator.ru/ — справочник вариантов размещения `AD_number`, `CHD_number`, `infnum`
- https://www.bgoperator.ru/texts/tour-api.html — создание заявки требует данные туристов/дат рождения и дополнительные условия

**Нельзя** выдумывать дату рождения из возраста, формировать условный `p` и выдавать вымышленный тариф за ответ API. В момент онлайн-расчёта backend получает состав по группам, сверяет его с категориями оператора, запрашивает право доступа к поставщику, при необходимости через защищённый сбор реальных дат рождения только на серверном этапе, проверяет идентификатор комнаты/питания, возрастные диапазоны, обе стороны перелёта, стоп-продажи, финальную общую цену и сроки действия котировки. Это отдельный функциональный этап, который **не реализуется** одним JavaScript-фильтром в статическом GitHub Pages.

## Необходимый backend contract перед включением продаж
`POST /v1/preview-quotes` для многокомнатных поездок должен принимать `rooms: [{adults: number, child_ages: number[]}]` и `preview_id` **только через HTTPS и авторизованную сессию**. Он должен проверять возраст в день вылета, несовпадения состава и наличие предложений для каждого номера, не использовать цены `TWO_ADULTS`. Ответ должен иметь `rooms_quoted`, `provider_price_scope`, `passenger_age_scopes_verified`, `total_rub`, `availability_verified`, `flight_verified`, `expires_at`, `currency` и идентификатор подтверждённого предложения. До работы backend JAMAICA **не отправляет** семейные или многокомнатные составы на устаревший two-adult-only endpoint и оставляет договор, оплату и бронирование отключёнными.

Даты рождения, паспортные данные, имена, токены и приватные данные не писать в GET URL, страницы GitHub Pages, логи и публичные JSON-файлы.

## Критерии готовности
1. 1 взрослый и ребёнок 7 лет: страница подробностей и проверки сохраняет именно 1+1 (7), не показывает цену за 2 взрослых.
2. 2 взрослых и дети 6/12, номер 2: 1 взрослый — точная группировка всех 5 человек на всех страницах.
3. Невыбранный возраст блокирует поиск, нельзя молча подставить 5 лет.
4. Для пары взрослых **в одном номере** возможно показать лишь подтверждённую справочную цену по прайсу (не live booking).
5. Пока backend не поддерживает защищённую проверку цены конкретного состава, никакая ссылка не переводит покупателя к оплате по фиктивной цене.
6. Активные каналы импорта, операторские API и расписания Oracle не должны неожиданно меняться от UI-коммита.

## Реализовано 22.11.2026 — закрытая серверная подготовка много-комнатной котировки

Исходники: `backend/bg_multiroom_quote.py`, `backend/bg_read_only_price_client.py` (`price_groups_only`), `backend/test_bg_multiroom_quote.py`.

- Приватный запрос строго воспроизводит **несколько `<group>`** в `<tour>`, отдельный `roommeal` и `sr` из операторского прайса на каждый номер и полный набор `persons` с реальными, защищённо полученными датами рождения. Не используется `<confirm/>`, который создаёт заявку.
- Перед любой сетевой попыткой проверяются идентификаторы исходного тура и гостиницы, даты, ночи, точное соответствие размещения и возрастной категории **каждого** пассажира на дату вылета, действительность документов. Дубли пассажиров между номерами и отсутствие любого подтверждения тарифного размещения блокируются.
- Для младенцев до двух лет не назначается место наугад: требуется источник `infant_policy_verified` и явное `WITH_SEAT` либо `NO_SEAT`; во втором случае требуется однозначный `parentnum` в своей группе, без повторного прикрепления к одному взрослому.
- Сумма розничной цены формируется только из отдельного подтверждённого значения `fullamount` для **каждой** группы. Поле `amount` — агентский нетто-платёж, его нельзя использовать для цены клиенту. Если есть общая сумма по всему туру, она должна совпасть с суммой по всем группам. При отсутствии группы, несовпадении валюты, сумм или клиента — ошибка, а не цена.
- Возврат результата маркируется `supplier_price_readonly=true`, `bookable=false`, `availability_verified=false`, `flight_verified=false`. Это **только ответ стоимости, не наличие мест или право принимать оплату**. Старый маршрут на двух взрослых и существующий contract-first каскад не расширялись автоматически.
- В модуле нет внешнего HTTP, токенов или логирования ПДн; клиент `BGReadOnlyPriceClient` осуществляет только авторизованный `POST` без переходов на сторонние домены. Приватная процедура не запускается по расписанию GitHub Pages. Секреты, ФИО, паспорта, дни рождения не должны попадать в публичный репозиторий, клиентский HTML или адресные параметры.

**Что остаётся для реальной цены семей:** авторизованный поставщиком и оператором доступ к личной серверной учётной записи, приватный сбор/проверка обязательных пассажирских данных с соответствующим правовым основанием, источник точных `roommeal` и `sr` для каждой группы по этой дате/отелю, бэкенд API со строго контролируемой аутентификацией и согласованием с договором и правами потребителя, повторные проверки мест и перелётов и настоящая система платежей. Заявлять оплату/подтверждённое бронирование до этих шагов нельзя.

Внимание: ограничения на количество комнат и возраст в JAMAICA — текущие ограничения клиентской формы, не универсальные границы Библио-Глобуса. Неподдерживаемые варианты должны честно возвращать статус неготовности, а не молча упрощаться до 2 взрослых.

## Проверка полноты возрастных тарифов из реального прайс-листа — 22.11.2026

Введён отдельный приватный, read-only слой `backend/bg_price_age_scope.py`. Он поддерживает реальные форматы диапазонов Библио-Глобуса: `[14-99][14-99]`, `12+,12+,2-11`, `[18-99],[18-99],[2-11]`. Возрастные границы включительные. Для каждого номера сверяется **весь состав** с возрастными ячейками тарифа через взаимно-однозначное сопоставление. Нельзя дважды использовать одну ячейку: два взрослых и ребёнок требуют три тарифных возрастных элемента.

**Важнейшее различие**:
- `possible_group(adults, child_ages, ag)` — *возможное* совпадение, потому что возраст конкретных взрослых на публичном сайте неизвестен. Наличие подходящего `ag` не подтверждает цену и вместимость комнаты.
- `exact_ages_match(ages, ag)` — сопоставление возрастов только после расчёта из реально проверенных дат рождения приватным операторским адаптером.
- `candidate_report(preview, selected_rooms, rows)` — счётчик кандидатов по группам, выбирающий только строки той же гостиницы, даты и продолжительности, с учётом операторских стоп-пометок. В первой группе дополнительно фиксируется номер исходного публичного превью; другие группы могут иметь другую комнату того же отеля, но ещё не согласованы в одной заявке.
- В `scripts/oracle_bg_selected_quote_probe.py` добавлен необязательный параметр `selected_rooms` к `inspect_selected`. При его наличии существующий авторизованный read-only сканер возвращает **только** агрегаты `group_age_candidate_counts` и `group_source_metadata_counts`. Не публикуются ссылки, идентификаторы из ответа, суммы, дети, ФИО, паспортные данные, XML, токены или прайсы.

Никаких цен семей, наличия мест, брони, новых стран или платежей это обновление само по себе не создаёт. Даже статус `POTENTIAL_CANDIDATES_ONLY` означает лишь найденные диапазоны возрастов. Для реальной цены надо связать каждую подходящую строку с `roommeal`, `sr`, официальным источником, получить точные даты рождения защищённым способом, выполнить авторизованный read-only запрос и независимо подтвердить места/рейсы/договор. Публиковать стоимость по одному только `ag` строго запрещено.

Документация оператора:
https://export.bgoperator.ru/load-xml-prices.html
https://www.bgoperator.ru/texts/api/tour-api.html

## Приватный запуск проверки возрастных вариантов

Сканер `scripts/oracle_bg_selected_quote_probe.py` поддерживает дополнительный аргумент `--private-rooms-file`. Использовать только после проверки авторизованного доступа к read-only цене и **только на доверенной машине**; не запускать внутри GitHub Pages или Actions с пользовательскими данными.

Файл содержит только взрослые/возраст детей/распределение по комнатам (без фамилий, паспортов и DOB), например:
```json
[
  {"adults": 2, "child_ages": [6, 12]},
  {"adults": 1, "child_ages": [4]}
]
```
Создать его локально вне каталога GitHub и выставить права `chmod 600`. Сканер отклоняет символьные ссылки, файлы других владельцев, групповые/публичные права доступа, содержимое больше 2048 байт и поля вне `adults/child_ages`. Возрастной состав не печатается в журнал.

```bash
python3 -B scripts/oracle_bg_selected_quote_probe.py \
  --directory /PRIVATE_ORACLE/destination-directory.json \
  --previews /PRIVATE_ORACLE/tour-previews.json \
  --preview-id p_<24_HEX_DIGITS> \
  --private-rooms-file /PRIVATE_ORACLE/rooms-0600.json
```

Строка `p_<24_HEX_DIGITS>` — только условное обозначение: нужен **настоящий** ID публичного предварительного предложения из приватно проверенной выгрузки, а не случайное значение. Путь к файлу и список возрастов не записывать в публичный репозиторий и не прикладывать к сообщениям с логами.

В выводе будут `AGE_GROUP_COUNT`, `AGE_GROUP_CANDIDATE_COUNTS`, `AGE_GROUP_SOURCE_METADATA_COUNTS`, `AGE_GROUP_STATUS`, `AGE_GROUP_QUOTE_VERIFIED=NO`. Это **не цены**, а количество вариантов. Подбор возраста лишь позволяет выбрать, какую официальную котировку запрашивать следующим этапом. Бронирование, платёж и подтверждение мест этим режимом не включаются.


## Уточнение формата прайс-листа и совместимости номеров (22.11.2026)

(основное размещение/roommeal), `sr`, `id_price` или `ic`, `dt` и
`o_duration` находятся на уровне строки `entries[]`, а `ag` — внутри
`prices[]`. Поиск `sr` внутри `prices[]` давал ложный ноль метаданных.

Идентификаторы, `sr`, персональные данные и суммы не выводятся публично.

## Протокол ответа поставщика: общая стоимость всего тура (22.11.2026)

При официальном `createtour` **без** `<confirm/>` ответ BG, раздел 3.1,
содержит `<tours><tour clientTourId="..."><sum>...</sum></tour></tours>`.
Под `tour` может быть несколько `sum` по разным валютам, например USD и RUR.
Официальный пример **не содержит** отдельного `<sum>` на каждый `<group>`.

Исправлен `backend/bg_multiroom_quote.py:parse_group_price_response`:
- Требуется совпадающий `clientTourId` и **ровно один** RUB/RUR `fullamount` на уровне `tour`.
- `amount` — агентская сумма к оплате, не стоимость для клиента.
- Возвращаемый `total_rub` относится ко всему запрошенному туру,
  `groups_requested` — число групп из приватного исходящего запроса,
  а не якобы подтверждённое количество отдельных сумм в ответе.
- `supplier_total_scope="WHOLE_TOUR"` и `group_price_breakdown_verified=false`
  для стандартного документированного ответа.
- Если расширение ответа содержит детализацию групп, она должна охватывать
  все группы и точно сходиться с суммой всего тура, иначе HOLD.
- В любом случае `bookable=false`, `availability_verified=false`,
  `flight_verified=false`. Никакие платежи и брони не включаются.

До подключения реальной семейной котировки остаются обязательными
приватное сопоставление источников `roommeal`/`sr`, наличие прав API,
безопасная обработка персональных данных, проверка отеля и двух перелётов.
Источник: https://www.bgoperator.ru/texts/tour-api.html#3 (раздел 3.1).


## Привязка к оригинальному prx и блокировка составного проживания (22.11.2026)

BG JSON содержит `prx` на верхнем уровне авторизованного прайс-листа и
`id_price`/`ic`, `id_ns`, `sr`, `dt`, `o_duration` в его строках.
Прежний агрегатор мог ошибочно принять строки с одинаковым `id_price`
из **разных** выгрузок как один совместимый многокомнатный тур.

Частный read-only сканер теперь в памяти привязывает каждую строку к её
исходному `prx`; счётчик общих источников принимает лишь совпадение
`prx + id_price/ic + дата начала основного проживания + длительность`.
`prx`, `sr`, суммы, паспорта и ID размещения в вывод не попадают.

Упрощённый сериализатор `backend/bg_multiroom_quote.py` передаёт только
основное размещение `roommeal`. Поэтому дополнительные размещения
`id_ns_b`, `id_ns_a`, `id_ns_ab`, `id_ns_ba` или расхождение
`dt/tour_date` и `o_duration/duration` блокируют источник до внедрения
полной маршрутизации; число возрастных кандидатов учитывается отдельно.
`POTENTIAL_SAME_PRX_PRICE_LIST_ONLY` не подтверждает совместимость
рейсов и наличие номера или цену. Сервис не делает брони и не принимает
платежей.

Официальный протокол:
https://www.bgoperator.ru/texts/load-xml-prices.html
https://www.bgoperator.ru/texts/tour-api.html
