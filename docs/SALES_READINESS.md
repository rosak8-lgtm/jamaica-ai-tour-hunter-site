# JAMAICA — состояние продаж и критерии запуска (20.11.2026)

## Что уже работает на опубликованном сайте

- Поиск по 251 корректному названию страны (в исходном официальном справочнике 252 записи, одна невалидная — \`x\` — скрыта).
- Указание Иркутска как города вылета для 13 направлений справочника; это **не** означает наличие рейсов на конкретную дату.
- Форма поиска тура: страна, город, дата, ночи, взрослые, дети, бюджет, отель.
- Результаты из \`verified-offers.json\`, если предложение свежее и прошло все проверки.
- Переход из карточки к внутренней странице \`/checkout.html?offer=...\`.
- Клиентский интерфейс без имён поставщиков, без WhatsApp и без e-mail-заявок.
- Строгое отключение онлайн-оплаты, пока продавец, система бронирования и PSP не готовы.
- GitHub Actions проверяют синтаксис JavaScript, маршрут покупки и серверную логику заказа.

## Не завершено — это блокеры реальных покупок

1. **Поставщик туров / бронирование:** известен только официальный справочник и исторические визуальные наблюдения. Есть ноль предложений с подтверждённой на данный момент окончательной котировкой, доступностью и правом публикации. Нужен серверный адаптер к разрешённым API актуального поиска, повторного расчёта и создания/подтверждения заявки. Проверка прайса не является бронированием.
2. **Подключение эквайринга:** нет юридически оформленного торгового счёта, реквизитов эквайринга, выбранной платёжной интеграции и подтверждённой тестовой транзакции. На Github Pages нельзя безопасно хранить секреты.
3. **Условия продавца:** в \`checkout-config.json\` отсутствуют юридическое название, регистрация, версия договора, правила аннуляции/возвратов, политика обработки данных и информация о документальной выдаче туров. Клиент должен видеть эти сведения до оплаты; скрывать имена источников в поиске можно, скрывать обязательные сведения договора нельзя.
4. **API-хостинг:** GitHub Pages — статический хостинг. \`backend/order_engine.py\` — логика контроля, **не** развёрнутая серверная служба. Нужен постоянный HTTPS API, CORS только с официального домена, аутентификация сессии покупки, антифрод, ограничения частоты, постоянная БД заказов и защищённый callback от банка.

## Контракт публикации предложения

\`verified-offers.json\`:
\`\`\`json
{
  "schema": "jamaica.verified-offers.v1",
  "generated_at_utc": "2026-11-20T00:00:00Z",
  "offers": []
}
\`\`\`

Каждая разрешённая к публикации запись должна содержать случайный непрозрачный \`id\`, \`origin\`, \`destination\`, \`hotel\`, \`depart_date\` (YYYY-MM-DD), \`nights\`, \`adults:2\`, \`children:0\`, \`total_rub\` (фактически подтверждённая сумма **за двоих**), \`quote_verified_at\`, \`expires_at\`, а также:
- \`publish_approved: true\`
- \`quote_verified: true\`
- \`availability_verified: true\`
- \`flights_out_green: true\` и \`flights_back_green: true\`
- \`price_scope_verified: true\`, \`total_two_verified: true\`
- если для исходного источника необходим специальный маркер, \`best_price_required: true\` и \`best_price_verified: true\`.

При отсутствии любого доказательства запись не должна публиковаться. В публичной выдаче **никогда** не раскрывать API-ключи, прямые URL кабинетов, внутренние идентификаторы поставщика и не выводить его торговую марку.

**Важное ограничение:** версия фронтенда сейчас реализует только точную цену для двух взрослых без детей. Одноместную или семейную цену нельзя вычислять умножением/делением чужой котировки. Для таких групп нужен отдельный подтверждённый расчёт и соответствующее расширение схемы.

Не загружайте историю из 2366 старых наблюдений как действующие цены. Пока \`offers: []\`, покупка должна быть недоступна.

## Контракт оформления

\`POST /v1/checkout/prepare\`:
- Сервер получает непрозрачный \`offer_id\`, ожидаемую цену и версию принятых условий.
- Проверяет реальную доступность и **повторно получает стоимость** у поставщика. Никакая цена из браузера не принимается без перепроверки.
- При отличии цены / отсутствии перелёта / занятости номеров — HTTP 409 и **без создания платежа**.
- Создаёт резервирование по авторизованному booking API, сохраняет заказ в постоянной БД с идемпотентным ключом и только затем создаёт платёжную сессию в подключённом банке.
- Возвращает \`{status:"PAYMENT_READY",order_id,status_token,total_rub,payment_iframe_url}\` только если платёжная форма допускает встраивание на сайт. При необходимости банковского redirect-flow нужен отдельный разрешённый согласованный механизм, а не несанкционированный iframe.
- Возврат браузера с платёжной страницы — **не** доказательство оплаты. Получение подтверждения банка обязательно независимо от браузера.
- После уведомления банка сервер проверяет платёж через официальный API и подтверждает бронь у поставщика; только после этого статус \`PAID_BOOKED\`.
- Если банк списал деньги, но бронь не подтверждена, статус \`REFUND_REQUIRED\`, запуск возврата и поддержка реконсиляции, но **не** фиктивная успешная бронь.
- Статус заказа доступен только по случайному токену покупателя; персональные данные и паспортные реквизиты не пишутся в логи.

## Подключение платёжной системы

Для бизнеса в Грузии техническая документация доступна на официальных сайтах [TBC E-Commerce](https://developers.tbcbank.ge/docs/checkout-overview) и [Bank of Georgia Payment Manager](https://api.bog.ge/docs/en/ipay). Возможность открытия торгового счёта, валюта приёма, направление платежей, возможность встраивания, возвраты, комиссии и требования к продавцу должны подтверждаться **конкретным договором**. Stripe не следует автоматически считать доступным для грузинского бизнеса.

Не размещайте merchant secret, токены агентства или API-ключи в GitHub, JavaScript, \`checkout-config.json\` или сообщениях чата. Храните их только в защищённом серверном менеджере секретов.

## Готовность к запуску реальных продаж

Продажи активируются только когда одновременно:
1. Из официальной системы получена свежая котировка и подтверждение всех составляющих тура.
2. Разрешено создавать резервирование/бронь от имени юридически уполномоченного продавца.
3. Оформлены договорные условия, отмены, обработка данных и документы, раскрыт продавец.
4. Подключён банк/PSP, тестовые платежи и обратные уведомления проверены, протестированы возвраты.
5. Развёрнут HTTPS API и постоянное хранилище, в котором можно достоверно отслеживать бронь и платёж.
6. Доказан end-to-end сценарий с реальной тестовой котировкой; состояние \`PAID_BOOKED\` получается только от серверных подтверждений.

До выполнения этих пунктов \`checkout-config.json\` должен оставаться \`live_booking_enabled:false, payments_enabled:false\`. Встроенные тесты **не равны** подтверждённой работе с банком или оператором.
