# JAMAICA — порядок визуальной проверки «ЛУЧШАЯ ЦЕНА» → два самолётика
23.11.2026 · синхронизация требований бота и клиентского сайта

## Проверено по официальному источнику

Библио-Глобус, инструкция «Бронирование заявок с разными датами
возвращения туристов», разделы «ШАГ 1» и «ШАГ 2»:
https://www.bgoperator.ru/pr_img/1000512/20260227/76496175/Konstruktor_-_raznye_daty_vyezda_-_Obnovlen.pdf

Сначала выбирают **город вылета** (в JAMAICA — строго Иркутск);
после выбора страны открывается **список маршрутов по датам**.
Именно в строке маршрута отображается «ЛУЧШАЯ ЦЕНА»;
только потом открывают расширенный подбор и конкретные отели/номера.

Нельзя:
- объявлять маршрут «ЛУЧШАЯ ЦЕНА» лишь по самой дешёвой строке отеля;
- переносить метку из одного маршрута/даты на другой;
- соединять самолётик туда от одного предложения с обратным от другого;
- принимать два зелёных цвета в карточке как фактически заключённую
  бронь или окончательно подтверждённую стоимость;
- выдавать 60 000 предварительных ссылок как уже проверенные туры.

## Что подтверждено текущим CLI

Проверка пользователя 23.11.2026 по пяти отдельным прайс-листам и
13 странам из настоящего опубликованного каталога:
- Таиланд: 482 тарифные позиции с двумя зелёными признаками из 1 110.
- Вьетнам: 3 336 из 3 624.
- Индонезия: 706 из 1 800.
- Китай: 0 из 142, оба направления по спискам под запрос.
- Остальные 9 стран: ноль в обследованных списках, в основном
  обозначения регулярных перелётов без однозначного числа мест.
- `BG_BEST_PRICE_MARKER_VERIFIED=NO` для всех этих результатов.
Числа относятся к исходным тарифным строкам, не к уникальным отелям
и не к бронированиям. Ещё не исследованы все даты/маршруты.

## Новая двухэтапная защита на сервере

`backend/bg_route_first_visual_gate.py`:
1. Строго проверяет браузерное доказательство метки в **выбранной
   строке маршрута** с происхождением `BG_OFFICIAL_BROWSER_ROUTE`.
2. Требует события перехода по этой строке, после которого бот
   проверил отдельно оба направления в точной строке
   `BG_OFFICIAL_BROWSER_SELECTED_DETAIL`.
3. Проверяет один и тот же закрытый сеансовый отпечаток, route ID,
   source price-list ID, страну, Иркутск, дату, гостиницу, тип номера,
   ночи и публичный ID выбранной карточки.
4. Проверяет строгий порядок событий и срок свежести до 15 минут.
5. Возвращает только булево значение. Сами URLs, ID поставщика,
   приватные сеансы, DOM, cookie, пароли и PII не публикует.

`backend/preview_quote_engine.py` теперь требует это
**дополнительно** к уже реализованным проверкам цен, гостиницы,
полётов и `best_price_verified`. Без всех нужных доказательств
частный оффер не создаётся. Важное уточнение: данные двух этапов
должен выдать реально авторизованный и изолированный серверный
браузерный модуль бота, а НЕ клиентский JavaScript.

Новая проверка — **контракт доказательств**, но она не является
самим Playwright-сканером. Без исходников установленного бота
неправильно обещать, что официальный UI уже изучен и DOM селекторы
могут работать в продакшене.

## Как посмотреть настоящую реализацию бота, не разглашая секреты

Последние известные локальные релизы содержат:
- `JAMAICA_V167_BG_VERIFIABLE_FUNNEL_20261122/bg_browser_v148.py`
- `JAMAICA_V167_BG_VERIFIABLE_FUNNEL_20261122/capture_bg_v148.js`
- `JAMAICA_V167_BG_VERIFIABLE_FUNNEL_20261122/visual_bridge_v148.py`
- более поздняя папка `JAMAICA_V183_DUAL_TELEGRAM_DELIVERY_20261123`

Выполнить на Lenovo:
```bash
(
set -Eeuo pipefail
cd "$HOME/Загрузки/jamaica-ai-tour-hunter-site"
git pull --ff-only origin main
python3 -B -m unittest -q \
  backend.test_bg_route_first_visual_gate \
  backend.test_bot_route_source_audit \
  backend.test_preview_quote_engine
python3 -B scripts/audit_bot_route_first_from_lenovo.py
)
```

`audit_bot_route_first_from_lenovo.py` использует только чтение и
AST, не исполняет бот, не запускает браузер, не отправляет Telegram,
не ходит в сеть и не печатает исходники или секретные значения.
Результат показывает точные файлы, SHA-256 prefix, имена методов,
номер строки и наличие признаков «маршрут → click → самолёты».
Статический аудит **не доказывает**, что бот в момент запуска
на самом деле нажал кнопку на сайте.

После определения точных функций и DOM-контрактов встроить реальный
приватный Playwright-проверяющий адаптер в JAMAICA, не копируя
Telegram-доставку в сайт. Обработчик должен при старте любого
оформления заново пройти два этапа и дополнительно авторизованно
запросить конечную цену, наличие гостиницы и договор/оплату.

Оба источника оператора в публичном сайте не рекламируются,
и сайт по-прежнему показывает все реальные страны с предварительными
предложениями. Для PEGAS отдельно действует его собственный
процесс; BG-маркер туда не переносится.

**Реальное оформление до подтверждённого supplier booking API,
договора продавца и PSP остаётся выключенным.**
